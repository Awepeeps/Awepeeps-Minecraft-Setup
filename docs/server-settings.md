# Server settings reference

This guide explains which layer owns common server behavior and how to trace a
setting back to its portable source. The template files are generic starting
points, not a dump of the current private deployment. Public TODOs and generic
defaults must not be filled by guessing at private runtime values.

## Sources of truth

| Layer | Source in this repository | What it controls |
|---|---|---|
| Panel and host automation | [`compose.yaml`](../compose.yaml), [`.env.example`](../.env.example), [bootstrap](bootstrap.md), [maintenance](maintenance.md) | Compose here defines the MCSManager panel and daemon; it does not define a Minecraft server container. `.env.example` is primarily local automation input. Keep real credentials and per-host values in ignored local files or the private deployment. |
| Vanilla server properties | [`server.properties.template`](../config/server.properties.template) | Authentication, allowlist enforcement, world identity and baseline game settings, network binding, RCON, and other vanilla server properties. |
| Vanilla world gamerules | [Paper defaults template](../config/paper-world-defaults.template.yml) and the commands in this guide | Per-world rules such as sleep percentage. Gamerules are saved with each world; they are not Paper default keys. |
| Paper defaults | [`paper-world-defaults.template.yml`](../config/paper-world-defaults.template.yml) | Paper-specific world defaults. The template is intentionally an empty merge point; keep the version key generated by the running Paper release. |
| Plugin behavior | [Plugin inventory](plugins.md), [configuration index](../config/README.md), and linked feature guides | Plugin-specific settings and behavior. Merge the relevant sanitized values into the config generated by the exact installed plugin release. |
| Runtime state | The saved Minecraft instance environment in MCSManager, the itzg-managed container, and generated files/world data | Authoritative for what that server is actually using. Check the saved instance environment, generated `server.properties`, world gamerules, and generated plugin configs together. |

MCSManager owns the Minecraft container lifecycle. Its saved instance
environment is passed to the itzg Minecraft image, which maps supported
variables to server properties at startup. For a setting supplied both ways,
the image environment is the startup input; the generated file and world data
show the effective runtime state. Document portable variable names and mappings
where useful, but keep actual values, panel identifiers, paths, addresses, and
credentials out of this repository. Exact image behavior can vary by image
version, so verify it against the selected image documentation and generated
runtime state.

Editing a template or a checkout file does not change a running server. Apply
intended changes to the saved Minecraft instance environment in MCSManager and
the relevant generated server or plugin files, then inspect the effective
runtime state. A local `.env` mirror used by host scripts is a reference for
those scripts; it is not authoritative for the Minecraft container.

## Access and identity

- Keep the server allowlist enabled and enforced. `ENABLE_WHITELIST` and
  `ENFORCE_WHITELIST` in the itzg environment should agree with the
  `white-list`/`allow-list` and `enforce-whitelist` properties supported by the
  selected Minecraft version. Check the version-specific property spelling.
  See [whitelist management](whitelist.md).
- Keep `online-mode=true` so Java accounts authenticate. Floodgate handles
  Bedrock identities; do not disable Java authentication to make Bedrock join.
- The template sets `enforce-secure-profile=false` for the Geyser/Floodgate chat
  compatibility case. This relaxes signed-profile enforcement for Java clients
  too; it does not turn off account authentication or the allowlist. Keep the
  trade-off visible and revisit it if the supported Geyser path changes.
- Add identities manually after owner approval. Whitelist contents, player
  names, UUIDs, and Floodgate state are private runtime data and never belong in
  the public template.

## World and gameplay settings

The portable [server properties template](../config/server.properties.template)
sets `gamemode=survival`, `difficulty=normal`, `pvp=true`, `view-distance=10`,
`simulation-distance=8`, `max-players=20`, `level-name=world`, an empty
`level-seed`, `spawn-protection=2`, and the default Java port `25565`. These are
the current
public template defaults, not a copy of a private instance's settings. The empty
seed creates a fresh random world; never publish a real seed or coordinates.
The template also sets `enable-command-block=false` and
`function-permission-level=2`; its RCON password is a placeholder and must be
supplied privately through the supported image environment. Review defaults for
the target server before applying them.

Spawn protection has two owners to keep aligned: the vanilla template sets
`spawn-protection=2`, while a selected spawn plugin can provide additional or
different protection. Do not change the public default based on a private
instance choice alone. When intentionally changing the portable policy, update
the template, the matching itzg `SPAWN_PROTECTION` value where used, and the
plugin behavior together.

Vanilla gamerules are set per world and stored with each world; sleep percentage
is not a Paper default. The portable reset policy sets and verifies
`minecraft:players_sleeping_percentage 50` in the overworld, Nether, and End.
After world creation, apply the same value to each intended dimension and read
it back, for example:

```text
execute in minecraft:overworld run gamerule minecraft:players_sleeping_percentage 50
execute in minecraft:the_nether run gamerule minecraft:players_sleeping_percentage 50
execute in minecraft:the_end run gamerule minecraft:players_sleeping_percentage 50
```

The value `50` is the portable reset policy. Runtime gamerules are persisted in
world data and do not come from `paper-world-defaults.template.yml`; the reset
automation reapplies and verifies the rule after it creates a new world.

## Network and service exposure

The Java server's default port is TCP 25565. Geyser's Bedrock listener uses UDP
19132 for RakNet and, for Bedrock 26.40+, NetherNet (TCP 19132 signaling plus
UDP 19133 media); confirm the plugin configuration and forward those ports
through the host's network as needed. Leave the Java `server-ip` property unset
inside the container unless the selected deployment requires a specific bind
address.
MCSManager panel and map exposure are host or reverse-proxy choices; the public
template does not authorize exposing management services to the internet. See
[Bedrock access](bedrock.md) and [BlueMap](bluemap.md).

RCON is used by some automation. Enable it through the supported image
environment and supply its password through a private secret mechanism. Do not
put an actual password in a template, example, log, or shared backup.

## Plugin settings

Plugin files are generated on first startup and can change shape between
releases. Stop the server before merging a template, preserve generated keys
that the template does not own, then check the plugin's startup log and effective
configuration. The [plugin inventory](plugins.md) says which plugin roles are
selected, test-only, deferred, or retired. In particular, don't treat
FreedomChat's `rewrite-chat` and `claim-secure-chat-enforced` as the same setting:
the public template's values describe only the public template policy, not any
private installation.

## Updating the portable policy

When a behavior changes, update its layer's template and this reference or the
linked feature guide in the same review. Check whether the itzg environment
overrides the file, whether a gamerule must be applied to existing worlds, and
whether a plugin provides the same behavior. Then update the public README and
decision log if the recommended stack changes. Do not infer public defaults,
pins, or test results from private deployment files; keep instance-specific
values and exact private pins there.
